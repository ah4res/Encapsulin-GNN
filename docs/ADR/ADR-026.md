# ADR-026

Date
2026-08-03

Track
Track B (Dry Research)

## Question

ADR-018により特徴量抽出モジュールを独立化し、ADR-024によりFeature Review工程を正式に導入した。また、ADR-025ではDatasetPreparationによる特徴量生成のバッチ実行を採用した。 【1-fa8a13】【2-538fbb】

次の段階として、Feature Review後の特徴量を選択し、Graph Datasetを構築する仕組みを実装する必要がある。

Graph構築では、

- どの特徴量を採用するか
- どの特徴量セットでGraphを作成したか
- どのGraph Datasetを学習に利用したか

が研究結果へ直接影響する。

また今後、

```text
FeaturesAA
FeaturesPLM
FeaturesConservation
FeaturesElectrostatic
FeaturesBfactor
```

などの新規特徴量モジュールや、

```text
Edge
EdgeFeatures
```

の追加拡張が想定される。

GraphBuilderは将来的なFeature追加に対して柔軟に対応できる必要がある。

GraphBuilderの責務をどのように定義するか。

## Decision

GraphBuilderを導入する。

GraphBuilderの主目的はGraph生成そのものではなく、

```text
Feature Selection
↓
Feature Merge
↓
Dataset Construction
↓
Experiment Tracking
```

を一体的に管理することである。

GraphBuilderは単なるMergeFeatures実装としては扱わない。

GraphBuilderは

```text
実験可能なGraph Datasetを構築し、
その構築条件を完全に再現可能な形で記録する基盤
```

として位置付ける。

また、GraphBuilderはFeatureモジュールや特徴量をハードコードしない。

処理対象となる特徴量およびFeatureモジュールは外部設定ファイルから取得する。

## Pipeline

全体パイプラインを以下のように定義する。

```text
DatasetPreparation
        ↓
Feature Review
        ↓
GraphBuilder
        ↓
Training
        ↓
Evaluation
```

GraphBuilderはFeature ReviewとTrainingの間に配置する。


## Scope

GraphBuilderの責務は以下とする。

### 1. Feature Selection

利用可能な特徴量の中から学習に利用する特徴量を選択する。

GraphBuilderはFeature Set定義を読み込み、利用する特徴量を決定する。

### 2. Feature Merge

各Featureモジュールの出力を統合する。

対象例

```text
FeaturesAA
FeaturesDSSP
FeaturesPISA
FeaturesContact
FeaturesPLM
Edge
EdgeFeatures
```

Node FeatureおよびEdge Featureを統合し、

```text
merged_node_features.csv
merged_edge_features.csv
```

を生成する。

### 3. Dataset Construction

Graph学習に利用する統合データセットを生成する。

初期実装では

```text
merged_node_features.csv

merged_edge_features.csv
```

を正式な出力とする。

### 4. Experiment Tracking

GraphBuilderの最重要責務とする。

Graph Dataset生成時に、

```text
どの特徴量を採用したか
どのFeature Setを利用したか
どの構造を利用したか
```

を必ず保存する。

Graph生成条件を完全再現できる状態を保証する。

## Feature Registry

GraphBuilderはFeature Registryを利用する。

配置

```text
GraphBuilder/feature_registry.yaml
```

Feature Registryは利用可能特徴量の単一情報源とする。

例

```yaml
charge:
  source: FeaturesAA
  type: node
  dtype: numeric

hydrophobicity:
  source: FeaturesAA
  type: node
  dtype: numeric

rsa:
  source: FeaturesDSSP
  type: node
  dtype: numeric

dssp_state:
  source: FeaturesDSSP
  type: node
  dtype: categorical

global_dasa:
  source: FeaturesPISA
  type: node
  dtype: numeric

actual_distance:
  source: EdgeFeatures
  type: edge
  dtype: numeric

ss_pair:
  source: EdgeFeatures
  type: edge
  dtype: categorical
```

新規特徴量の追加時はRegistryを更新する。

## Feature Set Definition

GraphBuilderはFeature Set定義ファイルを利用する。

配置

```text
GraphBuilder/feature_sets/
```

例

```yaml
name: FS-AA-DSSP

node_features:

  - charge
  - hydrophobicity
  - aromatic
  - polar

  - rsa
  - dssp_state

edge_features:

  - actual_distance
  - sequence_distance
```

GraphBuilderはFeature Setを参照しFeatureを選択する。

## Plugin Architecture

GraphBuilderはFeatureモジュール名や特徴量名をソースコードへハードコードしない。

GraphBuilderは

```text
FeaturesAA
FeaturesDSSP
FeaturesPISA
FeaturesPLM
EdgeFeatures
```

を直接認識しない。

GraphBuilderは

```text
Feature Registry
```

を参照し、

```text
利用可能特徴量
↓
特徴量の所属モジュール
↓
入力CSV
```

を解決する。

新規モジュール追加時は、

```text
feature_registry.yaml
```

を更新するだけで利用可能にする。

GraphBuilder本体の修正を必要としない構造を採用する。

## Feature Manifest

各Featureモジュールは自身の特徴量一覧を保持する。

例

```text
FeaturesAA/feature_manifest.csv
FeaturesDSSP/feature_manifest.csv
FeaturesPLM/feature_manifest.csv
```

GraphBuilderはFeature ManifestおよびFeature Registryを参照する。

## Graph Dataset ID

Graph Datasetごとに識別子を付与する。

例

```text
Graph-001
Graph-002
Graph-003
```

Graph Datasetは一意に識別可能とする。

## Output

Graph Datasetごとに専用ディレクトリを作成する。

例

```text
GraphBuilder/datasets/

    Graph-001/
```

出力内容

```text
Graph-001/

    merged_node_features.csv

    merged_edge_features.csv

    graph_manifest.json

    experiment_manifest.json
```

Graph生成結果はこのディレクトリのみで再現可能とする。

## Graph Manifest

Graph Dataset生成時にManifestを出力する。

例

```json
{
  "graph_id": "Graph-001",
  "feature_set": "FS-AA-DSSP",
  "pdb_count": 40,
  "node_feature_count": 35,
  "edge_feature_count": 4
}
```

## Experiment Manifest

特徴量選択条件を保存する。

例

```json
{
  "experiment_id": "EXP-001",

  "graph_id": "Graph-001",

  "node_features": [
    "charge",
    "hydrophobicity",
    "rsa",
    "dssp_state"
  ],

  "edge_features": [
    "actual_distance",
    "sequence_distance"
  ]
}
```

Graph Datasetと実験条件を紐付ける。

## Encoding Strategy

GraphBuilderは特徴量統合までを責務とする。

初期実装では、

```text
merged_node_features.csv
merged_edge_features.csv
```

生成までを対象とする。

機械学習用エンコードおよびPyTorch Geometric形式への変換は後続モジュールとして実装する。

## AI-driven Feature Exploration

GraphBuilderはAIによる特徴量探索を前提として設計する。

AIは

```text
feature_registry.yaml
```

を参照し、

利用可能特徴量の一覧を取得する。

例

```text
FS-AA

FS-AA-DSSP

FS-AA-PISA

FS-AA-DSSP-EDGE

FS-ALL
```

などのFeature SetをAIが提案可能とする。

GraphBuilderは人間およびAIが生成したFeature Setを実行可能とする。

## Rationale

今後の研究課題はGraph生成そのものではなく、

```text
どの特徴量を採用したか
```

による性能差の評価である。

そのため、

Graph Datasetは完全再現可能である必要がある。

また今後は新規Featureモジュールが継続的に追加されることが想定される。

GraphBuilderがモジュール名や特徴量名をソースコードへ埋め込む設計では、

新規モジュール追加のたびにGraphBuilder修正が必要となる。

これを避けるため、

```text
Feature Registry
+
Feature Set
```

によるPlugin Architectureを採用する。

この設計により、

```text
FeaturesAA
FeaturesPLM
FeaturesConservation
FeaturesElectrostatic
```

などの追加に対してGraphBuilderを変更せずに対応可能となる。

これはADR-018で採用した独立Featureモジュール思想をGraph構築層まで拡張するものである。 【1-fa8a13】

## Alternatives Considered

### Alternative 1

MergeFeaturesとして単純なCSV結合のみ実装する。

**Rejected**

実験条件を追跡できない。

### Alternative 2

GraphBuilderが各Featureモジュールを直接認識する。

**Rejected**

モジュール追加時にGraphBuilder修正が必要となる。

### Alternative 3

Feature Registryを利用したPlugin Architectureを採用する。

**Accepted**

再現性・保守性・拡張性が最も高い。

## Consequences

### Positive

- Graph Datasetの再現性を保証できる
- 特徴量採用履歴を保存できる
- AIによる特徴量探索に対応できる
- 新規Featureモジュール追加へ柔軟に対応できる
- GraphBuilder本体の修正頻度を低減できる
- 独立モジュール思想と整合する

### Negative

- Registry管理が必要となる
- Manifest管理が必要となる
- 初期実装の複雑性が増加する
